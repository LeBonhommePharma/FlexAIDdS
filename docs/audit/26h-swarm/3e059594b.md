# Audit: 3e059594b — Fix: Link Metal OBJCXX bridges via flexaid_core for Homebrew --with-metal

## Summary (2-4 sentences)
Commit `3e059594b95570b10b3d1c706e61cfcf243351ec` is a **correct, necessary CMake link-membership fix**: under `FLEXAIDS_USE_METAL=ON`, Metal OBJCXX bridges (`.mm`) and Metal/Foundation/MetalKit frameworks are attached **once** to the `flexaid_core` OBJECT library (PUBLIC frameworks + compile defs + metallib path macros), instead of only to `FlexAID` / `FlexAIDdS` executables. That closed the real Homebrew `--with-metal` failure mode where `flexaid_core` TUs (`gaboom`, `FOPTICS`, `hardware_detect`, `UnifiedHardwareDispatch`) referenced `metal_eval_*` / `metal_rmsd::*` while implementations lived only on some executables—undefined at link, especially with LTO and multi-target brew builds (`cavity_detect_cli`, `benchmark_datasets`, `flexaidds_process_ligand`). **No C++/ObjC++/science source edits.** Residual risks: Metal attach is still nested under `if(FLEXAIDS_BUILD_CORE)`, formula at this SHA only changes a comment (stable v2.0.2 remains unfixed until follow-ups/release), and this commit alone adds no link/nm gate.

## Severity: LOW–MEDIUM (residual); fix itself is HIGH-value / correct

The root bug was a **P0 packaging/link** defect for Apple Metal. The patch architecture is sound. Residual findings below do not reverse the main fix under default options (`FLEXAIDS_BUILD_CORE=ON`).

## Findings

### F1. Root-cause diagnosis is accurate and the membership model is right (INFO / positive)
- Evidence: Pre-commit, `target_sources(FlexAID PRIVATE LIB/metal_eval.mm …)` and a near-duplicate FlexAIDdS block; `LIB/CMakeLists.txt` explicitly said `metal_eval.mm` was “compiled directly into FlexAIDdS (not flexaid_core)” with linker expected to resolve symbols. That only works when the **same** executable also compiles the `.mm` files. Consumers that only `target_link_libraries(... flexaid_core)` still compiled Metal call sites because `target_compile_definitions(flexaid_core PUBLIC FLEXAIDS_USE_METAL)`:
  - `LIB/hardware_detect.cpp` → `metal_eval_get_capabilities`
  - `LIB/UnifiedHardwareDispatch.cpp` → `metal_eval_get_capabilities` + Shannon Metal
  - `LIB/gaboom.cpp` → `metal_eval_init` / `metal_eval_batch` / multi-batch
  - `LIB/FOPTICS.cpp` → `metal_rmsd::compute_pairwise_rmsd_metal` / `is_metal_rmsd_available`
- Parent incomplete consumers:
  - `cavity_detect_cli` (default **ON**): linked `flexaid_core`, attached **only** `CavityDetectMetalBridge.mm` → still missing `metal_eval_*` from core TUs.
  - `flexaidds_process_ligand` (optional): linked `flexaid_core` with **no** Metal sources.
  - `benchmark_datasets`: parent re-attached a partial bridge set (workaround commit `612cccb72`); still duplicated and easy to drift (e.g. TurboQuant missing from that list).
- Fix: `_FLEXAIDS_METAL_BRIDGES` on `flexaid_core` + `target_link_libraries(flexaid_core PUBLIC Metal/Foundation/MetalKit)` + PUBLIC defs (`FLEXAIDS_USE_METAL`, `FLEXAIDS_HAS_METAL_SHANNON`, `FLEXAIDS_HAS_METAL_TENCM`, `*_METALLIB_PATH`). OBJECT library objects are linked into each consumer; LTO sees the implementing TUs in the same link unit.
- Why it matters: This is the correct CMake ownership model for an OBJECT core library. Executable-only bridge attachment was structurally wrong once more than one target linked `flexaid_core`.
- Fix recommendation: Keep this model. Do not reintroduce per-exe Metal source lists for `flexaid_core` consumers.

### F2. Metal attach is nested under `FLEXAIDS_BUILD_CORE` while some Metal consumers are outside (MEDIUM)
- Evidence: `if(FLEXAIDS_BUILD_CORE)` opens at root `CMakeLists.txt` ~L166; Metal attach block is ~L271–412; `endif() # FLEXAIDS_BUILD_CORE` is ~L890. **Outside** that fence:
  - `cavity_detect_cli` (default ON) — links `flexaid_core`
  - `benchmark_datasets` (default ON) — links `flexaid_core`
  - gtest targets such as `test_dataset_runner` / `test_cofactor_blacklist` — link `flexaid_core`
- With default `FLEXAIDS_BUILD_CORE=ON` (from `cmake/FlexAIDOptions.cmake`), Metal is attached before those targets and the brew path is fine.
- Config `FLEXAIDS_BUILD_CORE=OFF` + `FLEXAIDS_USE_METAL=ON` + `ENABLE_CAVITY_DETECT_CLI=ON` (or any other out-of-core `flexaid_core` consumer):
  - `LIB/CMakeLists.txt` still sets `PUBLIC FLEXAIDS_USE_METAL` on `flexaid_core`
  - root never runs `target_sources(flexaid_core PRIVATE … .mm)`
  - link fails again with undefined `metal_eval_*` / related symbols
- Why it matters for build/repro: Homebrew formula does not flip `FLEXAIDS_BUILD_CORE`, so production brew is safe. CI or partial builds that disable core executables but keep cavity/benchmark/tests can reintroduce the exact class of bug this commit fixed.
- Fix recommendation: Move the entire “Metal sources (attach to flexaid_core once)” block to **immediately after** `add_subdirectory(LIB)` (and optional Components/Helpers includes), **outside** `if(FLEXAIDS_BUILD_CORE)`. Keep metallib custom targets and PUBLIC defs on `flexaid_core` regardless of which executables are enabled.

### F3. Formula change is documentation only — stable `--with-metal` still broken at this SHA (MEDIUM for packaging, not for HEAD tree)
- Evidence: `Formula/flexaidds.rb` only rewrites the install comment. Still:
  - `url` / `sha256` → **v2.0.2** tarball (pre-fix)
  - `head` → `branch: "master"` (no HEAD-only Metal enforcement yet)
  - No `odie` for stable+metal; no `ENABLE_CAVITY_DETECT_CLI=OFF` shrink
- Follow-up `5a3b95430` (ancestor of PR #260 packaging path) refuses stable `--with-metal`, points HEAD at the fix branch, and disables auxiliary targets. Release `600e95ba9` / v2.0.3 carries the CMake fix into a tagged tarball.
- Why it matters: Operators reading only this commit’s formula comment may believe `brew reinstall --with-metal` on **stable** is fixed; it is not until HEAD or a release that contains this CMake change.
- Fix recommendation: Treat formula correctness as a **chain**: this commit (CMake) + `5a3b95430`/`12f3a6a08`/`99e5b35eb` (formula/docs) + v2.0.3. Do not claim “Homebrew Metal works on stable” from `3e059594b` alone.

### F4. Secondary correctness win: FlexAID now gets `SHANNON_METALLIB_PATH` (LOW–MEDIUM positive)
- Evidence: Parent compiled `ShannonMetalBridge.mm` into **FlexAID** with `FLEXAIDS_HAS_METAL_SHANNON` but **did not** set `SHANNON_METALLIB_PATH` on FlexAID—that path macro was only under the FlexAIDdS Metal block. Child compiles Shannon metallib once and sets `SHANNON_METALLIB_PATH` **PUBLIC** on `flexaid_core` (all consumers, including FlexAID).
- Why it matters: Without the path, runtime load of `ShannonEntropy.metallib` falls through to failure/fallback paths even when the bridge was linked. Unifying metallib compile + PUBLIC path macros is a real functional improvement for classic FlexAID Metal Shannon, not just a link cleanup.
- Fix recommendation: Keep single shared metallib set. Eventually install `.metallib` beside shipped binaries and prefer runtime-relative discovery over absolute `CMAKE_CURRENT_BINARY_DIR` paths (see F6).

### F5. Dedup of FlexAIDdS `*_ds.metallib` is correct; alias targets preserved (INFO / positive)
- Evidence: Parent built parallel `CavityDetect_ds.metallib`, `TurboQuant_ds.metallib`, `MetalRMSD_ds.metallib` for FlexAIDdS with distinct path macros. Child builds one set and adds:
  - `CavityDetectMetalDS` / `MetalRMSDMetalDS` / `TurboQuantMetalDS` aliases
  - `CAVITY_METALLIB_DS` / `RMSD_METALLIB_DS` / `TQ_METALLIB_DS` var aliases for helpers
- Why it matters: Cuts redundant `metalc` work and avoids divergent shader artifacts between FlexAID and FlexAIDdS. Alias names prevent silent breakage of older `add_dependencies(... CavityDetectMetalDS)` call sites.
- Fix recommendation: Prefer canonical names (`CavityDetectMetal`, …) in new code; keep aliases until greps are clean.

### F6. Metallib paths remain build-tree absolute; brew install does not stage `.metallib` (LOW, pre-existing)
- Evidence: Bridges load `@CAVITY_METALLIB_PATH` / `@METALRMSD_METALLIB_PATH` / `@SHANNON_METALLIB_PATH` / `@TURBOQUANT_METALLIB_PATH` as filesystem URLs (e.g. `MetalRMSDBridge.mm`, `CavityDetectMetalBridge.mm`, `ShannonMetalBridge.mm`). Paths expand to `${CMAKE_CURRENT_BINARY_DIR}/…metallib`. Formula installs Mach-Os under `libexec/bin` and data matrices, not metallibs.
- Why it matters: Link succeeds (this commit’s goal); **runtime** Metal shader load on a Homebrew-prefix machine may still miss the build-dir metallib and rely on inline compile / default-library fallbacks. Pre-existing packaging gap; widened only in that more targets now embed the same absolute macros via PUBLIC defs.
- Fix recommendation: Install `*.metallib` next to binaries (or under `libexec/share/metal/`), define paths relative to executable / `FLEXAIDDS_DATA_DIR`, and document fallback behavior. Optional CI: after install prefix, assert GPU path either finds metallib or logs a controlled fallback.

### F7. `flexaids_attach_metal_dispatch_runtime` guard is good but incomplete (LOW)
- Evidence: Helper now returns early if `LINK_LIBRARIES` MATCHES `flexaid_core` (avoids duplicate `metal_eval.mm` when a target both links core and calls the helper). Still attaches only `metal_eval.mm` + `ShannonMetalBridge.mm` (+ Shannon path/deps)—appropriate for standalone `hardware_detect` / `UnifiedHardwareDispatch` unit tests (`test_hardware_detect_dispatch`, `test_unified_dispatch`, `benchmark_dispatch`).
- Gaps (mostly pre-existing):
  - `get_target_property(... LINK_LIBRARIES)` does not always see generator-expression / interface-only edges; rare false negative → possible duplicate-symbol if a target links core via a non-obvious path.
  - Standalone tools that compile `hardware_detect.cpp` / `UnifiedHardwareDispatch.cpp` **without** `FLEXAIDS_USE_METAL` on the target and without the helper (`tencom_entropy_diff`, `benchmark_tencom`, python `_core`) simply compile Metal branches **out**—no link failure, but no Metal on those binaries even when global Metal is ON.
  - `tENCoM` / `ligand_tencom_pose` still attach `tencm_metal.mm` privately (they do **not** link `flexaid_core`)—correct isolation; no double-symbol with core.
- Why it matters: Does not re-break brew FlexAID/FlexAIDdS. Incomplete Metal coverage on auxiliary/Python targets can confuse “I built with `-DFLEXAIDS_USE_METAL=ON`” expectations.
- Fix recommendation: For any target that compiles Metal-gated call sites, either link `flexaid_core` or call a single attach helper. Prefer `get_target_property(... INTERFACE_LINK_LIBRARIES)` + recursive check, or a target property `FLEXAIDS_HAS_METAL_BRIDGES` set on `flexaid_core` and queried by the helper.

### F8. OBJCXX / standard flags and double PUBLIC `FLEXAIDS_USE_METAL` (LOW / hygiene)
- Evidence:
  - `set_source_files_properties(... COMPILE_FLAGS "-std=c++26 -fno-objc-arc")` while AppleClang CXX often defaults to **C++23** in this project’s top-level logic.
  - `FLEXAIDS_USE_METAL` set PUBLIC on `flexaid_core` in both `LIB/CMakeLists.txt` and the root Metal block.
  - Target-level `-fno-objc-arc` plus per-source `COMPILE_FLAGS` redundancy.
- Why it matters: Unlikely to break link; can cause OBJCXX vs CXX standard skew warnings or subtle ABI/template differences in shared headers. Duplicate defs are harmless.
- Fix recommendation: Drive OBJCXX standard from `CMAKE_CXX_STANDARD` / `CXX_STANDARD` target property; drop hard-coded `-std=c++26` in `COMPILE_FLAGS`. Single ownership for `FLEXAIDS_USE_METAL` (LIB define for core TUs; root only for bridges/frameworks/metallib).

- Follow-up `ffa7499cd` / `metal-self-hosted.yml` later add shader compile smoke + optional `nm` for `metal_eval_*` / `metal_rmsd`—the right verification, but **not** part of `3e059594b`.
- Why it matters: Future CMake refactors can reintroduce executable-only membership without a failing test on PR CI (hosted macOS often cannot full-link Metal GPU paths).
- Fix recommendation: Keep blocking Metal self-hosted (or at least `nm` after `cmake --build` with Metal ON) for any change touching `_FLEXAIDS_METAL_BRIDGES`, `flexaid_core` Metal defs, or Formula metal option. Add a configure-time or unit check that every target linking `flexaid_core` under Metal either inherits bridge sources or is explicitly allow-listed.
