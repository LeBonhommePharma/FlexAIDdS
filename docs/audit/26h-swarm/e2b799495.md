## Findings

### F1. New “blocking” macOS gate was **red on the PR head and still merged** (HIGH)

- Evidence (check-runs on `ffa7499cd`, branch `fix/audit-macos-ci-gate`):
  - Job **macOS CPU tests (blocking)**: **failure** (configure+build OK; **Test (ctest blocking)** failed).
  - Same PoseBust failures on Linux `cxx_core_build` cells (gcc/clang/mpi/asan).
  - **Metal shader compile smoke**: **success** — `Metal compile smoke: SUCCESS (5 shaders)`, `status=ok`.
  - PR body test plan still unchecked (`[ ] PR CI: macos_cpu_tests runs and is required`).
  - Merge time 2026-07-15T04:32:14Z while head still had failed ctest conclusions from ~03:37–04:21Z runs.
- ctest signature (macOS + Linux identical class):
  ```text
  PoseBustEngine.DefaultBackendIsNativePoseQC
  PoseBustDatasetRunnerContract.NativeBackendMapsPbPassFromFullSuite
  Expected: resolve_backend_from_env() == Backend::Native
  Actual:   4-byte object <00-00 00-00>   # enum 0, not Native
  ```
  (from `tests/test_posebust.cpp` ~L427, ~L471.)
- Why it matters: AGENTS.md requires zero test failures before push and “verify with actual execution.” Enabling a gate that correctly fails is good; **shipping the gate while red** means main never had a demonstrated green macOS CPU ctest at the moment the policy claimed victory. PoseBust default-backend regression is **pre-existing product/test debt exposed by the gate**, not introduced by the YAML—but merge discipline still failed.
- Fix recommendation:
  1. Fix `resolve_backend_from_env()` / test env assumptions so default is `Backend::Native` (or update tests if intentional Auto=0).
  2. Re-run `macos_cpu_tests` + Linux `cxx_core_build` to green on main.
  3. Never merge when the new gate is red unless an explicit waiver is recorded in `docs/CI_RELEASE_GATES.md`.

### F2. GitHub ruleset does **not** enforce required status checks (HIGH)

- Evidence:
  - Classic branch protection API: **disabled** (`404`).
  - Ruleset `Protected: branch` (id `13682749`): only `deletion` + `non_fast_forward`. **No** `required_status_checks` / merge queue.
  - Therefore a red `macOS CPU tests (blocking)` job cannot stop a GitHub UI merge by an admin.
- Why it matters: Docs and CONTRIBUTING call the job “blocking,” but **repository policy does not implement that word**. Operators can re-introduce the F1 failure class indefinitely.
- Fix recommendation: Add required checks (at minimum):
  - `macOS CPU tests (blocking)`
  - `C++ core (linux-gcc)` / `C++ core (linux-clang)`
  - `Metal shader compile smoke` (optional: allow success-only; soft-skip is still exit 0)
  - `Repository hygiene (env + agent paths)`
  Document the required-check names exactly as GHA displays them (rename-sensitive).

### F4. Hosted Metal smoke soft-skip can be misread as “Metal validated” (MEDIUM)

- Evidence:
  - Script exit **2** → job sets `status=skipped`, prints `::notice`, **exits 0**.
  - Docs at this commit say soft-skip does not authorize Metal release claims (good), but do **not** yet have the later “Allowed vs forbidden release language” table (`8c42517bd`).
  - Job name “Metal shader compile smoke” shows green in the PR checks UI whether `ok` or `skipped` unless someone opens the notice.
- Why it matters: Badge-driven or checklist-driven release managers may tick Metal green when metalc was absent. On this PR, smoke was genuinely **ok** (5 shaders)—so the immediate merge was not a false skip—but the design remains claim-risky.
- Fix recommendation: Keep exit-0 skip for hosted runners without metalc; add a workflow summary annotation or required output artifact (`metal_smoke_status=ok|skipped|failed`). Prefer later release-language table; never equate soft-skip with production Metal.
