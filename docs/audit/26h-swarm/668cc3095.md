## 2. S1 / S2 / S3 definitions — contract vs code vs repo doctrine

### 2.1 Normative table (contract + three-engine §1.4)

| ID | Definition | Role |
|----|------------|------|
| **S1** | Elected (top-1) pose RMSD ≤ 2.0 Å | **Primary / claim KPI** |
| **S2** | S1 ∧ PoseBusters pass on elected pose | Modern secondary |
| **S3** | Any emitted cluster pose RMSD ≤ 2.0 Å (BCR / any-pose ceiling) | **Diagnostic only** |

Hard rules enforced in docs + CLI:

1. Never report S3 as abstract / headline success.
2. Always report S1, S2, S3 separately on claim rows.
3. Election gap = S3=1 ∧ S1=0; report counts; do not fold into S1.

### 2.2 Implementation at this SHA

```text
RMSD_SUCCESS_A = 2.0   # inclusive upper bound: 0.0 <= x <= 2.0

is_s1:
  reject if seed_echo truthy
  if success_s1 present and non-blank → honour flag   ← FLAG-FIRST
  else if finite elected RMSD → 0.0 <= rh <= 2.0
  else success_rmsd / success fallbacks
  else False

elected_rmsd:
  rmsd_hungarian → rmsd_to_crystal
  (no rmsd_top1 yet — three-engine schema primary field missing)

is_s2:
  require s1
  prefer success_pb if present, else pb_pass
  missing PB columns → False (S2 fail-closed on PB absence)  ✓

is_s3:
  if success_s3 present → honour flag   ← FLAG-FIRST
  else finite best_cluster_rmsd / rmsd_bcr ≤ 2.0
```

### 2.3 Alignment with PoseBusters / RMSD ≤ 2 doctrine

| Source | Claim “success” language | Relation to this commit |
|--------|--------------------------|-------------------------|
| **This contract** | Headline = **S1** (RMSD-only elected); S2 secondary | Self-consistent |
| **three_engine §1.4 / H4** | Same; H4 expects S2 \< S1 and report both | Aligned |
| **README success table** | S1 primary, S2 secondary, S3 diagnostic | Aligned |
| **AGENTS.md** | “Successful only when RMSD ≤ 2.0 **and** PoseBusters pass; never report RMSD-only as benchmark success” | **Conflict** — S1 as primary is RMSD-only |
| **BENCHMARK_STANDARD.md** | Success = `rmsd_hungarian` **\<** 2.0; historical “BCR” headline confused elected Hungarian with any-pose | **Threshold** `≤` vs `<`; this commit **correctly demotes** any-pose S3 from headline |

**Science judgment:**

- Demoting S3/BCR from abstract success is a **major integrity win** relative to older BCR-as-headline language.
- Making **S1 (RMSD-only)** the claim KPI is intentional for three-engine queue comparability (FlexAID arms may lack PB). For **FlexAIDdS “claim-ready / modern” tables**, AGENTS still expects **S2** (or an explicit dual column set). The contract mitigates by always emitting S2 and by labelling S1 clearly, but agents must not quote S1 as “PoseBusters-validated success.”
- Threshold **≤ 2.0** vs BENCHMARK_STANDARD **\< 2.0**: inclusive bound is common in docking literature and matches three-engine §1.4; boundary cases exactly at 2.0 Å will be counted here and **not** under strict `< 2.0` scripts. Document and freeze one convention in methods.

### 2.4 Demonstrated flag-first integrity hole (commit-era)

Reproduced from commit semantics (not HEAD):

| Row | Commit `is_s1` |
|-----|----------------|
| `success_s1=1`, `rmsd_hungarian=9.0` | **True** (stale flag wins) |
| `rmsd_hungarian=9.0`, no flag | False |
| `success_s1=1`, `rmsd_hungarian=-1` (sentinel) | **True** |
| `rmsd_hungarian=-1`, no flag | False (`0.0 <= -1` fails) |
| `rmsd_hungarian=2.0` | True (inclusive) |

Same class of issue for **S3**: `success_s3=1` with `best_cluster_rmsd=9` would count as S3 hit.

**Fix-forward:** `9dbbd9fa9` inverts to **finite RMSD always wins over flags** for S1/S3.

## 3. Claim admission — fail-closed analysis

### 3.1 Contract gates

A row is claim-eligible only if **all** of:

| Check | Required |
|-------|----------|
| `seed_echo` | **0** |
| `native_pose_seeded` | **0** |
| `matrix_md5` | equals campaign matrix pin |
| `protocol_claim_eligible` | if present and non-blank: must be true |

Default matrix pin: `72d7c7396702331d96ff12d18f831796` (`MC_st0r5.2_6.dat`), overridable by CLI → `RUN_RECEIPT.json` → `provenance.json` → default.

### 3.2 Code: `_flag0` at this SHA is **fail-open** on missing

```text
# 668cc3095
missing / None / blank  →  True  (treat as 0 → ADMIT)
"0" / False / false / NO / no  → True
"0.0"  → False  (REJECT — treats 0.0 as non-zero!)
"1"  → False
```

| Case | Admit at `668cc3095`? | Fail-closed ideal? |
|------|----------------------|--------------------|
| Explicit `seed_echo=1` | Drop ✓ | Drop |
| Explicit `seed_echo=0` | Admit ✓ | Admit |
| **Missing** `seed_echo` column | **Admit ✗** | Drop |
| **Blank** `seed_echo` | **Admit ✗** | Drop |
| `seed_echo=0.0` | **Drop ✗** (false positive reject) | Admit |
| Missing per-row `matrix_md5` | Admit under campaign pin ✓ (by design) | OK if campaign pin trusted |
| Wrong per-row `matrix_md5` | Drop ✓ | Drop |

**Contract marketing vs code:** enforcement line claims *“fail-closed claim filters”*, but implementation docstring of `_flag0` explicitly documents *“missing → treat as 0 for admission”* for older CSVs. That is **fail-open provenance**, not fail-closed science admission.

**Risk:** A campaign CSV that never wrote seed columns (or iCloud-thinned rows that lost columns) can enter claim aggregates as if proven no-seed. For three-engine P3 tables this is unacceptable.

**Fix-forward:** `9dbbd9fa9` makes missing/blank fail admission and accepts `"0.0"`.

### 3.3 Double path on seed_echo

- **Admission** uses `_flag0` (missing → pass).
- **`is_s1`** uses `_truth(seed_echo)` (missing → not truthy → S1 still computable).

So missing seed_echo neither drops the row nor blocks S1. Explicit `seed_echo=1` both drops (admission) and zeros S1 if a row somehow stayed in claim set.

### 3.4 Matrix pin

- Per-row empty → campaign-level pin applies (documented).
- Mismatch → drop with `matrix_md5_mismatch` reason (tested).
- At this SHA: **no 32-hex validation** of pin string (added later); garbage CLI pin would silently filter almost everything via mismatch.

### 3.5 `protocol_claim_eligible`

Present and false → drop; missing → no extra gate. Matches contract “missing → recompute from seed flags.”

## 9. Residual risks / operator pitfalls

1. **Quoting S1 as “PoseBusters-validated”** — violates AGENTS; always pair S1 with S2 for FlexAIDdS modern claims.
2. **Quoting S3 without “diagnostic” label** — blocked by CLI for headline, still possible if an agent scrapes `metrics.S3.rate` from JSON and re-labels.
3. **Missing seed columns → silent claim admission** at this SHA.
4. **Flag-first S1/S3** can launder bad RMSD/sentinel into success.
5. **Point rates without CI** can be over-interpreted as final science.
6. **≤ vs \< 2.0** mismatch with BENCHMARK_STANDARD aggregation snippets.
7. **`success_pb` preferred over recomputing `s1 ∧ pb_pass` from raw columns** — still AND-gated by local `s1`, so S2 ≤ S1, but if `success_pb` is 0 while `pb_pass=1` and s1 true, S2 under-counts (prefers engine composite).
